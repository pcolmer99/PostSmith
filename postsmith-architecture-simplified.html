The one idea, and the piece that proves it

Two things in the diagram above carry the whole architecture: a fixed opening that the agents are reached through, and one small piece of software that plugs a browser into it. Everything else is detail.

THE SEAM · THE FIXED OPENING

run(config, invocation_state=None, *, progress_callback=None)
IN PLAIN TERMS

A seam is one agreed opening where two halves of a system meet, and its shape never changes. Think of the serving hatch in a restaurant kitchen. Waiters never walk into the kitchen, chefs never walk into the dining room, and every order and every finished plate crosses at the hatch.

Because the hatch keeps the same shape, you can redecorate the dining room, swap the waiters for a delivery app, or move the kitchen to another building, and nobody has to reinvent how food gets ordered.

Here the hatch is a single instruction: hand the agent a job description, get back a finished, ranked list. That shape was agreed on day one and has not changed since. A web page, a laptop launcher and a managed AWS service have all been attached to it, and not one of them required a change to the agent doing the work.

That is the payoff, and it is worth being blunt about: get the opening right early and every new feature simply attaches to it. Get it wrong and every new feature becomes surgery on the part that already works.

In technical terms: one synchronous, orchestrator-agnostic call. Three independent adapters, zero changes to the pipeline. It is also why a human clicking a button can stand in for a scheduled orchestrator without the agents noticing the difference.

THE BRIDGE · WHAT PLUGS INTO THE OPENING

IN PLAIN TERMS

The agent works like a colleague who disappears for two minutes and comes back with a finished report. There is nothing to see until it lands. A browser needs the opposite: something visible every few seconds, or the person watching assumes it has frozen.

The bridge is the member of staff standing at the hatch. It carries the request in, calls out what the agent is doing while it is doing it — gathering stories, dropping ones already covered, scoring, ranking — so the screen fills in live, then brings the finished list back out. The agent never had to learn how to talk to a browser. The bridge absorbed the entire difference.

It is also the locked door. The browser only ever speaks to the bridge, so the keys to the AWS account stay on the far side of the hatch and never reach anyone's screen. A web page cannot ask for a real, billable run; only the server side gets to decide that.

And whether a run succeeds or fails, the answer comes back in the same shape: a list that is either full or empty, plus a note if something went wrong. One thing to read, never two.

In technical terms: FastAPI and Server-Sent Events. A per-request queue, worker thread and cancel flag turn one blocking call into a live event stream. AWS credentials resolve server-side only, and the front-end cannot request a live run. Bound to loopback and unauthenticated on purpose, because it is a local development surface.

Talk abstract

Breakfast session · approximately 40 minutes.

Find the seam first: building an agentic system that survived three rewrites of everything around it.

AWS ships around 3,000 announcements a year. A practitioner who wants to post about them in their own voice, without getting facts wrong, has effectively taken on a second job — and generic AI tools produce bland, off-brand, occasionally incorrect output. PostSmith was built to solve that. This talk is not about the prompt. It is about the seam.

PostSmith grew across five specifications, and every one plugged into a single Python function signature decided on day one and never changed. Three later features — a browser interface, a local launcher, and a managed AWS runtime on Bedrock AgentCore — each attached to that one callable as an independent adapter. None of them modified the agent.

We will walk the arc. Act one builds the agent deliberately unplugged: ports and adapters for feeds, model, and storage, so the entire pipeline runs offline on fixtures with no AWS account. Act two builds the human review surface against mock data, before any wiring exists at all. Act three connects the two with a streaming bridge, touching neither side. Act four is a launcher — the boring spec with the sharpest edges, where reliably killing a process tree turned out to be genuinely hard. Act five deploys the agent to AgentCore Runtime, where the additive-adapter pattern pays for itself: no new credential code, no pipeline changes.

Along the way: why determinism is a feature, why every proposed topic starts excluded so the human opts in rather than out, why every failure is shaped exactly like a success, and what we found when the deployed agent turned out to be emitting no traces at all.

You will leave with a method: find the seam first, keep an offline path behind every port, and write down the decisions you rejected.
